Notes core — porting the Livewire notes feature to React + Inertia

This is a strawman of how I intend to rebuild the notes list and the note editor on the new stack — put here for you to argue with before I write any code. The list/CRUD is routine; the real risk is the editor, so most of the reasoning below is about that. Skim the decisions and the "where I'm guessing" section and push back — a sentence from you now saves a rewrite later.

Background

How the notes feature works today, and what changes on the new stack

The domain (unchanged). A note has a title, a markdown body, a type (fleeting/literature/permanent/structure/project), and a URL slug. Notes link to each other: typing [[Some Note Title]] in the body creates a "mentions" connection to that note. The reverse direction is a backlink. Notes also carry tags.

What Livewire did. In the old app a single page component held both the server state (the note, its tags, its links) and the interaction logic, talking to the server over a persistent "wire". The body textarea used wire:model.live.debounce.1500ms — every pause in typing shipped the value to the server and re-rendered. A separate Alpine.js file (note-editor.js) ran the purely-client bits: the Write/Preview tab, the "saved/saving/unsaved" label, and the [[ autocomplete popover (which fetched /notes/search directly).

What stays exactly the same. The entire backend below the controller — NoteService, the DeleteNote action, NotePolicy, the Note/Tag models, the [[wikilink]]-to-connection sync, the embedding job, and the NoteSearchController JSON endpoint — is plain Laravel and ports verbatim. (This is the thesis of docs/architecture-inertia.md: only the entry point is stack-specific.)

What changes. The Livewire page component splits in two: a thin Laravel controller that returns props, and a React page that renders them. There is no persistent wire — the browser gets serialized props and changes server state by visiting a route. The Alpine file becomes React hooks. That split is the whole job of this slice.

The approach

Rebuild two pages — notes/index and notes/show — as React components fed by a thin NoteController, reusing the existing services untouched. Treat the note's saved state as an Inertia prop, and everything transient in the editor (which tab, the save indicator, the [[ popover) as local React state.

Intuition

Think of the old Livewire page as one person doing two jobs at once — clerk (talks to the database) and typist (handles the keyboard). Inertia splits them by a hard wall. The clerk stays on the server (the controller + services), hands the typist (React) a photocopy of the note, and the typist can only change the record by filing a request back through the wall. The editor autosave is the typist quietly filing an updated copy every time you stop typing — and showing a little "Saving… / Saved" note so you trust it happened.

The autosave, concretely

The one genuinely fiddly behaviour. In Livewire the debounce lived in a Blade attribute. On the new stack it becomes an explicit React effect: local state holds the draft title/body; when they change we mark status unsaved, wait for a 1.5s pause, then PATCH the note; while in flight, saving; on success, saved. The server response confirms and (crucially) returns freshly-reconciled links/backlinks, because saving the body re-parses [[wikilinks]] into connections.

Intended shape

The controller is a thin dispatcher — authorize, delegate to the service, return props. Two read actions and the writes. (Coarse — real signatures are spec's job.)

NoteController — entry points
index(request):   authorize viewAny
                  props = NoteService.listForUser(user, q, tagId)  // paginated
                        + tagsForUser(user)
                  render 'notes/index'  with {notes, tags, filters:{q,tagId}}

show(note):       authorize view
                  props = note (+tags) , outgoingLinks, backlinks, availableTags
                  render 'notes/show'

store(request):   authorize create ; note = NoteService.createForUser(...)
                  redirect -> notes.show(note)          // fresh page = the editor

update(note,req): authorize update ; NoteService.updateWithLinks(note, validated, user)
                  redirect back            // props (note, links, backlinks) come back fresh

destroy(note):    authorize delete ; DeleteNote.run(note) ; redirect -> notes.index

The editor page's local state — everything the server does not need to know until save. This is the Alpine object, re-expressed as one hook.

useNoteEditor(note) — client-only editor state
draft   = { title, body }         // seeded from the note prop
status  = 'saved' | 'unsaved' | 'saving'
tab     = 'write' | 'preview'

on draft change:  status = 'unsaved'
                  debounce 1.5s -> PATCH update(note) with draft
                                   status = 'saving' ... on success 'saved'

// wikilink popover is its own hook, below

The [[ autocomplete — the trickiest client piece. It watches the caret, and when the text just before it is an unclosed [[…, it searches and shows a popover. Ported straight from note-editor.js.

useWikilinkAutocomplete(textareaRef) — the [[ popover
on keystroke / click in textarea:
    look at text before caret
    match /\[\[([^\]]*)$/   // an open "[[" with no closing "]]" yet
    no match  -> hide popover
    match     -> query = captured text
                 debounce 200ms -> GET /notes/search?query=&exclude=
                 show results (or "searching…" / "no matches")

on pick(result):  replace the open "[[…" with "[[Title]]" , restore caret , hide
keyboard:         ↑ / ↓ move highlight , ↵ pick , esc close   // NEW vs Livewire

Design decisions — contest these

Keep the raw-markdown <textarea> + a Preview tab. Do not adopt a rich-text / WYSIWYG editor.

The whole linking model is text-based ([[Title]] parsed server-side), the source app is deliberately a plain-text markdown editor, and a textarea is the lowest-risk faithful port. It also keeps the caret math for the [[ popover simple (a real editor hides the caret behind its own model).

Rejected: TipTap / Lexical / CodeMirror. Real power, but they change the editing model, complicate wikilink detection, add bundle weight, and turn a 1-slice port into its own project. If we want this, it's a deliberate later slice, not a smuggled-in default.

Autosave = local draft state + a debounced PATCH, with a partial reload that pulls back only note, outgoingLinks, backlinks.

Mirrors the old 1.5s debounce. Saving re-parses the body into connections, so links/backlinks genuinely change on save and must refresh — but the tags panel and page chrome don't, so a scoped reload (Inertia only:) avoids re-shipping the whole page on every pause.

Rejected: (a) save-on-blur only — loses the "it's saving as I think" feel the app is built around. (b) A manual Save button — same. (c) Full-page reload on every save — wasteful and flickers the sidebar.

Title and body autosave through the same debounced channel; creating a note stays a separate explicit store.

On show both fields are just draft — unifying them means one save path, one status indicator. But creating (from the index) is a title-only intent that should redirect you into the editor, so it stays its own action, exactly as today.

Rejected: Separate save paths for title vs body — two debounce timers racing, two status sources. Rejected for one source of truth.

The [[ popover calls /notes/search via Inertia's useHttp (a plain JSON request), not a router visit.

It's a background lookup that must not swap the page or touch props — precisely the case docs/architecture-inertia.md reserves useHttp for. The existing NoteSearchController already returns the right JSON, so the endpoint is reused as-is.

Rejected: raw fetch (what Alpine did) — works, but re-implements credentials/CSRF/error handling that useHttp gives for free and keeps consistent with the rest of the app.

Split the client logic into two hooks — useNoteEditor (draft + autosave + tabs) and useWikilinkAutocomplete (the popover) — not one big component.

They have independent lifecycles and the popover is reusable later (the same [[ UX will want to appear in other note surfaces). Matches the app's existing resources/js/hooks/ convention.

Rejected: one monster <NoteEditor> holding all state — harder to test, and couples caret logic to save logic that have nothing to do with each other.

Scope: this slice ships in list · create · live-search · tag-filter · delete · the editor · links/backlinks. It stubs the assist panel and the "Find connections" modal.

The show page in the source embeds <assist-panel> and <connections-modal> — those are slices 6 (AI Assists) and 2 (Connections). I'll leave a visible placeholder where they mount so the layout is right and the later slices drop in cleanly.

Rejected: pulling connections/assists forward to "finish show in one go" — that's the un-sliceable big-bang we explicitly chose against.

Basic tag attach/detach/create rides along in this slice (it's welded into the show sidebar), but tag management as a feature belongs to slice 2.

The editor sidebar is unusable without at least showing and adding tags, and the index tag-filter needs the tag list. So the minimum tag surface comes now; anything richer (renaming, colors, a tags page) waits.

Rejected: deferring tags entirely — would leave the ported show visibly broken vs. the original.

Where I'm guessing

The honest gaps. These become the grill's opening agenda.

Markdown rendering for the Preview tab.

The Livewire version fakes markdown with a handful of regex replacements (headings, bold, code, [[links]]) — deliberately tiny. On React I'd default to a real renderer (react-markdown + a remark plugin for [[wikilinks]]) for correctness. But that's a new dependency and a behaviour change (real markdown vs. the app's intentional subset). Do you want a faithful port of the regex-subset, or an upgrade to real markdown now? This is also a taste/scope call, not just technical.

Where wikilink resolution and rendering should happen in preview.

In preview, [[Title]] should ideally render as a real link to that note if it exists (and a "create?" affordance if it doesn't). The source just renders a dead # anchor. I'm assuming a dead-link faithful port for this slice and deferring "resolve + click to navigate" — confirm that's acceptable, or it grows the slice.

List style and tag-filter placement.

I'm assuming a faithful port: card-per-note list + an inline tag-chip filter row, matching the original. Research surfaced denser-table (Zoom) and filter-popover (Frame) alternatives. I'll port faithfully unless you'd rather restyle now — but restyling is better as its own taste pass than mixed into a stack migration.

Note-type on create.

The source always creates a Fleeting note from the index (title only), and type changes elsewhere. I'm assuming that stays. If you want a type picker at creation time, that's a small addition but a behaviour change worth naming.

Autosave conflict / navigation safety.

The source doesn't guard against navigating away mid-save, and Livewire's wire made it mostly moot. On an SPA I'd consider a "you have unsaved changes" guard and flushing a pending debounce on unmount. I'm assuming we match the source (no guard) for parity, but flag it — it's a real UX gap the port could quietly fix.

Search backend availability in the target app.

NoteService.listForUser and searchForUser use Laravel Scout + Meilisearch. I'm assuming the target app will run the same Scout/Meilisearch setup (it's a backend port, not a rewrite). If the target is meant to start on the database driver instead, the search path changes. Needs confirming before implement.
