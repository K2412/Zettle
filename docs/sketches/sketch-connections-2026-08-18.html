Design sketch · before the code

Connections — linking two notes with a named relationship

/pair slice 2 · a NEW feature (the source app has no manual version) · touches app/Http, app/Services/Note, resources/js/components/notes/*, the notes/show sidebar

A strawman for how I'd let you say, in your own hand, "this note supports that one" — and see it from both sides. This is a new capability the old app never had (it only made links by typing [[wikilinks]] or let an AI propose relationships). Argue with the Design decisions and Where I'm guessing sections — the directionality choice especially. Redirecting here costs a sentence; after the build it costs a rewrite.

Background

What already exists, and the one invariant we must not break

The edge is already in the database. Notes-core built a connections table: a directed edge — a source_note_id, a target_note_id, a relationship (one of 18 enum values), an optional rationale, unique on the triple (source, target, relationship). So the storage for this feature is done; this slice is the authoring and display on top of it.

Two kinds of edge share that one table. Today every row is a mentions edge, created automatically when you type [[Another Note]] in the body. This slice adds authored edges — supports, contradicts, depends_on, etc. — that you make by hand.

The invariant. When you save a note, the server re-reads the body and rebuilds the mentions edges from the [[links]] it finds (NoteService::syncLinksFromBody). It only touches mentions rows. So authored edges already survive a re-save — but every part of this slice has to keep honouring that line: never let the wikilink sync see or delete an authored relationship, and never let authoring write a mentions row.

Where it shows up. The notes/show sidebar already has a "Links to" and a "Backlinks" list (built from all outgoing/incoming edges today) and a dashed "Find connections — coming in the Connections slice" placeholder. That placeholder is where this lands.

The approach

Add a Connections panel to the note sidebar: a list of the note's authored relationships (both the ones it asserts and the ones pointed at it), and a "+ Connect" control to make a new one — pick a target note, pick a relationship, optionally say why.

Intuition

Think of it like the "Linked issues" box in a bug tracker — "blocks PROJ-12", "is blocked by PROJ-9". You pick the other ticket and the kind of link. Here the links are ideas, not tickets: "this note supports [Spaced Repetition]", "this note depends on [Working Memory]". And like a tracker, the other note automatically shows the mirror image — open Working Memory and it says "required by [this note]", without you entering anything twice.

The mirror image, concretely — the load-bearing bit

The edge is stored once, on the note that asserted it. The other note computes what to show by flipping the relationship to its inverse name. Some relationships have a distinct inverse; some read the same both ways.

Intended shape

The inverse map is the heart of the model — one place that both the display and the API read. Coarse; the full 18-entry table is spec's job.

Relationship::inverse() — one source of truth for the mirror
inverse(rel):
  directed pairs:   supports↔supported_by, depends_on↔required_by,
                    explains↔is_explained_by, example_of↔has_example, ...
  symmetric:        contradicts, analogous_to, tension_with, distinguishes_from
                      -> return themselves
  (some inverses are display-only labels, not new enum cases — see decisions)

Design decisions — contest these

Store the edge once (directed) and compute the inverse for display — do not write two rows.

The table is already a directed edge with a uniqueness constraint. One row per assertion keeps writes simple, avoids the two-rows-out-of-sync bug, and matches how issue trackers do "blocks / is blocked by". The other note computes its label from inverse(relationship).

Rejected: writing a reciprocal row on the target (double-entry) — doubles storage, invites drift, and complicates delete. Also rejected: a symmetric/undirected edge — loses the direction "A supports B ≠ B supports A".

Keep authored connections in a NEW "Connections" panel, separate from the existing "Links to" / "Backlinks".

"Links to"/"Backlinks" are [[wikilink]] mentions — "I referenced this". Authored connections are "I assert this relationship". They mean different things; mixing them muddies both. The new panel groups by relationship label; mentions stay as-is.

Rejected: folding typed connections into the existing lists — a reader couldn't tell a casual mention from a deliberate "contradicts". Also rejected: relabelling the mention lists — they're fine; they just aren't this.

Author inline in the sidebar (a "+ Connect" that expands a picker), not a full-screen modal.

The picker is small — a note typeahead, a relationship dropdown, an optional rationale line. Inline keeps you next to the note you're connecting and reuses the sidebar you're already in. The research's incident.io modal is the alternative, and the old stub was named "modal", but inline is lighter for a three-field form.

Rejected: a modal over the whole page — heavier than the interaction needs, and it hides the note you're linking from. (If the relationship list needs a lot of room, this flips — see guesses.)

Reuse /notes/search (the [[ endpoint) as the target picker; POST authored edges via a normal Inertia <Form>/visit.

The typeahead already exists, is tested, and excludes the current note. Authoring is a real mutation that should go through Inertia (redirect + partial reload of connections/incoming), unlike the background [[ lookup which uses a plain fetch.

Rejected: a second search endpoint — needless duplication. Also rejected: optimistic client-only insert — the server owns the uniqueness + ownership checks; a visit keeps one source of truth.

Edit a connection's relationship + rationale in place (PATCH); also allow remove.

Changing your mind about how two notes relate ("this actually qualifies, not supports") is common in synthesis; forcing remove-then-re-add loses the rationale and is clumsy. A small edit affordance on each row.

Rejected: remove + re-add only — simpler to build but worse for the core "refine your thinking" use, which is the whole point of the vocabulary.

Where I'm guessing

The honest gaps — these open the grill.

Which of the 18 relationships to expose, and how.

Eighteen is a lot for a dropdown. I'm guessing a curated primary set (supports, contradicts, qualifies, extends, depends_on, example_of, explains) shown first, with the rest under a "more…" group — and I'd hide the two system types (mentions, provenance) entirely, since those aren't hand-authored. Is that the right default set? Should they be grouped by kind (evidential / structural / dialectical)? This is a domain call only you can make.

The inverse map — the exact labels.

I can pair the obvious ones (supports↔supported by, depends_on↔required by, explains↔is explained by, example_of↔has example). But several are judgement calls: is corrects's inverse "corrected by"? Is raises_question_about symmetric or "questioned by"? Is contradicts truly symmetric (I assumed yes)? And should these inverse labels be display-only strings, or real enum cases? I'm leaning display-only (don't bloat the enum), but that's a call.

Rationale — required or optional?

I assumed optional (fast to connect, add the why later). But a Zettelkasten purist might argue an untyped-reason connection is noise, and requiring a sentence forces real thinking. Your methodology, your call.

Inline vs modal (and whether the stub's name binds us).

I proposed inline. The old code left a stub literally named connections-modal-stub, and the research's cleanest patterns (incident.io, Plane) are modals. If you picture this as a focused "link two notes" modal — maybe reachable from a keyboard shortcut — say so and I'll flip it; it changes where the picker state lives.

Do authored connections influence the graph / anything downstream?

I'm scoping this to author + display on the note page only. But typed connections are exactly what a graph view (slice 5) would color edges by, and what a structure note would read. I'm assuming no downstream coupling this slice — connections are just created and shown — and deferring graph/structure use. Confirm that boundary.
